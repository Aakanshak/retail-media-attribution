# Power BI Data Model

## Recommended semantic model

Use a star-oriented model in Power BI even though PostgreSQL stores some
dimensions in normalized form. PostgreSQL normalization protects data quality;
the Power BI model should optimize filter propagation and measure clarity.

### Fact tables

| Power BI table | Source | Grain | Primary business use |
|---|---|---|---|
| `FactAdEvents` | `fact_ad_events` | One ad event | Funnel, spend, CTR, CVR, pacing |
| `FactOrders` | `fact_orders` | One product order | Revenue, units, organic share, customer behavior |
| `FactCustomerJourney` | `fact_customer_journey` | One customer-product path | Journey length and conversion-path analysis |
| `FactAttributionResults` | Attribution long output | One model-channel result | Model credit, attributed revenue, attributed ROAS |

`FactAttributionResults` should use the long-format columns generated by
`data/processed/attribution_model_comparison_long.csv`:

| Column | Data type |
|---|---|
| `model` | Text |
| `channel` | Text |
| `funnel_stage` | Text |
| `attributed_conversions` | Decimal number |
| `conversion_credit_share` | Decimal number |
| `attributed_revenue` | Currency/decimal |
| `spend` | Currency/decimal |
| `attributed_roas` | Decimal number |

Preferred production pattern: load this output into a PostgreSQL table or view
named `fact_attribution_results`, then connect Power BI to it with the same
PostgreSQL source. For the first portfolio build, importing the long CSV into
Power BI is acceptable, but document it as a model-output artifact rather than
raw source data.

### Dimensions

| Power BI table | Source or construction | Notes |
|---|---|---|
| `DimDate` | DAX calculated date table | Shared reporting calendar |
| `DimCampaign` | `dim_campaigns` merged with `dim_advertisers` | Include advertiser brand, category, and tier |
| `DimProduct` | `dim_products` | One row per product |
| `DimCustomer` | `dim_customers` merged with RFM query output | Customer profile and refreshed RFM attributes |
| `DimChannel` | Distinct channel rows from attribution output | Split campaign type and placement if useful |
| `DimAttributionModel` | Distinct model rows from attribution output | First Touch, Last Touch, Linear, Time Decay, Markov, Shapley |

## Power Query shaping

### Flatten campaign and advertiser attributes

In Power Query:

1. Load `dim_campaigns`.
2. Merge it with `dim_advertisers` on `advertiser_id`.
3. Expand:
   - `brand_name`
   - advertiser `category` as `advertiser_category`
   - `tier` as `advertiser_tier`
   - `join_date` as `advertiser_join_date`
4. Name the result `DimCampaign`.
5. Disable load for the staging `dim_advertisers` query if it is not otherwise
   needed.

This avoids a `DimAdvertiser -> DimCampaign -> FactAdEvents` snowflake and makes
campaign type, brand, and advertiser tier slicers filter the event fact through
one relationship.

### Add date-only fields to fact tables

Power BI relationships should use dates rather than timestamp columns. Add:

```powerquery
Event Date = Date.From([event_timestamp])
Order Date = Date.From([order_timestamp])
Path Start Date = Date.From([path_start_timestamp])
Path End Date = Date.From([path_end_timestamp])
```

Keep the original timestamp columns for drill-through and hourly analysis.

### Merge RFM into the customer dimension

1. Load the result of `sql/queries/rfm_segmentation.sql` as a staging query.
2. Merge it into `dim_customers` on `customer_id`.
3. Expand:
   - `recency_days`
   - `frequency`
   - `monetary_value`
   - `recency_score`
   - `frequency_score`
   - `monetary_score`
   - `rfm_code`
   - `customer_segment`
4. Name the merged table `DimCustomer`.
5. Disable load for the RFM staging query.

Merging keeps customer segment as a true dimension attribute, so a segment
slicer filters both event and order facts through the existing customer
relationships. It avoids a bidirectional one-to-one relationship.

### Shape the attribution dimensions

Create reference queries from `FactAttributionResults`:

- `DimAttributionModel`: distinct `model`
- `DimChannel`: distinct `channel`, `funnel_stage`

Optionally split `channel` on `" | "` into:

- `channel_campaign_type`
- `channel_placement`

Do not relate `DimCampaign` directly to `FactAttributionResults`: the
attribution output is aggregated at channel, not campaign, grain.

## Relationships

Use single-direction filters from dimensions to facts.

| From | To | Cardinality | Active | Cross-filter |
|---|---|---:|---|---|
| `DimDate[Date]` | `FactAdEvents[Event Date]` | 1:* | Yes | Single |
| `DimDate[Date]` | `FactOrders[Order Date]` | 1:* | Yes | Single |
| `DimDate[Date]` | `FactCustomerJourney[Path End Date]` | 1:* | Yes | Single |
| `DimCampaign[campaign_id]` | `FactAdEvents[campaign_id]` | 1:* | Yes | Single |
| `DimProduct[product_id]` | `FactAdEvents[product_id]` | 1:* | Yes | Single |
| `DimProduct[product_id]` | `FactOrders[product_id]` | 1:* | Yes | Single |
| `DimProduct[product_id]` | `FactCustomerJourney[product_id]` | 1:* | Yes | Single |
| `DimCustomer[customer_id]` | `FactAdEvents[customer_id]` | 1:* | Yes | Single |
| `DimCustomer[customer_id]` | `FactOrders[customer_id]` | 1:* | Yes | Single |
| `DimCustomer[customer_id]` | `FactCustomerJourney[customer_id]` | 1:* | Yes | Single |
| `DimChannel[channel]` | `FactAttributionResults[channel]` | 1:* | Yes | Single |
| `DimAttributionModel[model]` | `FactAttributionResults[model]` | 1:* | Yes | Single |

### Role-playing dates

Create these inactive relationships only when the report needs alternate date
roles:

| Relationship | Purpose |
|---|---|
| `DimDate[Date] -> DimCampaign[start_date]` | Campaign launch analysis |
| `DimDate[Date] -> DimCampaign[end_date]` | Campaign end analysis |
| `DimDate[Date] -> DimCustomer[signup_date]` | Signup/cohort analysis |
| `DimDate[Date] -> FactCustomerJourney[Path Start Date]` | Journey-start analysis |

Measures can activate an inactive relationship with `USERELATIONSHIP`.

## Date table

Create this calculated table:

```DAX
DimDate =
VAR MinEventDate =
    MINX ( FactAdEvents, FactAdEvents[Event Date] )
VAR MaxEventDate =
    MAXX ( FactAdEvents, FactAdEvents[Event Date] )
RETURN
ADDCOLUMNS (
    CALENDAR ( MinEventDate, MaxEventDate ),
    "Year", YEAR ( [Date] ),
    "Quarter Number", QUARTER ( [Date] ),
    "Quarter", "Q" & QUARTER ( [Date] ),
    "Month Number", MONTH ( [Date] ),
    "Month", FORMAT ( [Date], "MMM" ),
    "Year Month", FORMAT ( [Date], "YYYY-MM" ),
    "Year Month Sort", YEAR ( [Date] ) * 100 + MONTH ( [Date] ),
    "Week Number", WEEKNUM ( [Date], 2 ),
    "Day of Week Number", WEEKDAY ( [Date], 2 ),
    "Day of Week", FORMAT ( [Date], "DDD" ),
    "Is Weekend", WEEKDAY ( [Date], 2 ) >= 6,
    "Promotion Period",
        SWITCH (
            TRUE (),
            [Date] >= DATE ( 2024, 8, 5 )
                && [Date] <= DATE ( 2024, 9, 8 ), "Back-to-School",
            [Date] >= DATE ( 2024, 11, 18 )
                && [Date] <= DATE ( 2024, 12, 31 ), "Holiday",
            "Standard"
        )
)
```

Then:

1. Mark `DimDate` as the date table using `DimDate[Date]`.
2. Sort `DimDate[Month]` by `Month Number`.
3. Sort `DimDate[Year Month]` by `Year Month Sort`.

## Fields to hide

Hide technical fields from report view:

- all surrogate/string IDs except those needed in drill-through;
- raw FK columns on facts;
- timestamp columns when a date field is sufficient;
- `ordered_touchpoints` JSON;
- sort helper columns;
- staging queries used only for merges.

Keep IDs visible in a dedicated drill-through folder if interviewers need to
trace a customer journey or campaign.

## Avoid these relationship mistakes

- Do not relate fact tables directly to one another.
- Do not create a relationship from `FactOrders[purchase_event_id]` to
  `FactAdEvents[event_id]` in Power BI. It creates fact-to-fact filtering and is
  unnecessary for standard report measures.
- Do not use bidirectional relationships as a shortcut.
- Do not relate `FactAttributionResults` to `DimCampaign` because the result
  grain is channel, not campaign.
- Do not use the JSON journey array as a Power BI relationship key.
